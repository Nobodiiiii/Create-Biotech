# 仿生生物特殊体块特性表与施工方案

依据：[手术台供体基础特性调研](bionic-donor-traits-survey.zh-CN.md)。适用版本为本分支的 Minecraft 1.21.1、NeoForge 21.1.234、Create 6.0.10-281。本方案中的“特殊体块”指需要原始解剖角色及装配用途共同决定的头、鳃、腿、足、翅、鳍、尾、刺、壳、口器和攻击手等；现有全体块体质继续由 `BionicBodyTraitRegistry` 负责。

## 二、当前工程的施工起点

- [`BionicBodyTraitRegistry`](../src/main/java/com/nobodiiiii/createbiotech/entity/trait/BionicBodyTraitRegistry.java) 已做供体探测、逐项数据覆盖和按保留体块数量汇总；[`SlimeBionicEntity`](../src/main/java/com/nobodiiiii/createbiotech/entity/SlimeBionicEntity.java) 已执行部分全体块能力。特殊器官不能直接加入该枚举后继续按全身占比汇总。
- [`SurgicalAssembly.Source`](../src/main/java/com/nobodiiiii/createbiotech/content/surgery/SurgicalAssembly.java) 目前保存 `presentCubes` 和保留下来的 `headCubes`，但没有原始完整头部集合、其他解剖角色及单块权重。`SurgicalSubject.removeComponent` 会删去已切离的头部标记，故仅靠现有 `headCubes` 无法计算原头部完整度。
- [`SurgicalCapturedRenderPlan`](../src/main/java/com/nobodiiiii/createbiotech/content/surgery/client/SurgicalCapturedRenderPlan.java) 在客户端借 Create 帽子定位识别头部；[`BionicMind`](../src/main/java/com/nobodiiiii/createbiotech/entity/ai/BionicMind.java) 已按保留头部汇总认知。现有 `NECK/SHOULDER/HIP/ELBOW/KNEE` 关节与 `effectiveLimbs()` 可以用于装配用途，但不能替代供体原始器官标记。
- 服务端的 [`SurgicalTableBlockEntity`](../src/main/java/com/nobodiiiii/createbiotech/content/surgery/SurgicalTableBlockEntity.java) 会接收客户端发现的体块数量、接缝和头部集合。新增战斗或免疫能力时，不能把客户端提交的器官标记直接当作权威事实。

## 三、数据与合并规则

### 1. 保存供体来源和原始器官

为每个原始供体建立稳定的 `donorId`，随切割、打包、拆箱和再次装配传递。为原始体块保存 `originalRoles`、可选 `weights` 和布局版本；`presentCubes` 仍表示当前保留体块。切离出来的碎片继承同一 `donorId` 和原始角色全集，不能把碎片重新视为“完整器官”。读旧存档时，旧 `headCubes` 只能标为“已知保留头块、原始完整度未知”，不能假装完整度为 100%；旧档仍保留现有 `BionicMind` 行为，新增特殊能力待可信解剖映射补齐后才解锁。

角色建议至少有 `HEAD/GILL/TORSO/WEIGHT_BEARING_LEG/FOOT/LEFT_WING/RIGHT_WING/FIN/TAIL/TENTACLE/SHELL/SPINE/MOUTH/ATTACK_HAND`。一块可持有多个角色。原始角色用于判断器官身份，`effectiveLimbs()`、实际落地腿、攻击手选择和连接图用于判断装配后能否工作。头只需与身体连通，不强制要求脖子关节。

服务端采用受信的生物类型/稳定变种解剖模板或显式适配器，按原始体块 ID 映射角色和权重，并验证布局版本、体块数量、拓扑与边界。客户端捕获结果仅用作可视化和候选提示。缺少受信模板的模组供体仍可获得已有全体块特性，特殊器官状态记为 `unknown`；不能因为未识别头/翅就断言该物种没有该器官。模板应允许微小生物一块多角色，并对 GeckoLib、动态模型等无法稳定编号的模型提供人工适配入口。

### 2. 逐项规则与来源优先级

新建独立于 `bionic_body_traits/` 的器官规则目录，按特性 ID 保存自动探测开关、实体类型标签规则、单个生物规则、适用角色、完整度门槛和效果参数。逐项覆盖顺序与现有体质一致：`自动探测 < 实体标签 < 单个生物`；`false` 可取消较低优先级结果。探测结果区分 `present / absent / unknown`。只允许读取实体类型、稳定白名单状态和经过审查的查询；不从当前装备、药水、姿态、AI 目标或一次攻击试验提取永久器官能力。

原版现成标签只作为“该物种可能有能力”的事实来源；例如 `fall_damage_immune` 还需拆成材料、飞行和猫科落地等不同部位规则。生物族标签如 `spider_like` 是本模组拟新增的语义标签，不能当成原版已有标签。初期以原版生物模板覆盖可核验的器官；对未知模组采用保守回退，并让数据包和 Java 适配器补充。

### 3. 成品计算

对同一 `donorId`、同一器官角色的体块先取并集，按原始体块 ID 去重。器官完整度定义为

`q = 该器官已保留且连通的原始体块权重之和 / 该器官原始体块权重之和`。

权重优先使用服务端模板给出的有效体积/质量；没有可信权重时可在同一供体内暂用每块等权，并在面板明确标示近似。不得以切割后的 `Source` 数量或成品的全身体块数量充当器官分母。`q` 达到该特性的公开门槛后，再检查用途条件：承重腿需要有效髋/膝链和落地接触；翅、鳍需要正确的推进方向与负载能力；攻击器官需要匹配实际命中的那一手/口器；壳需覆盖主要躯干且进入防御姿态。连通性按现有接缝、胶合和关节图计算，断开的碎片不贡献有效器官。

二值交互能力由一个有效头解锁，多个头仍只保留一套成品主人关系。运动能力按有效器官完整度、数量、方向及 `bodyVolume` 负载计算，不能靠增加碎块数量叠强度。附效攻击与部位命中绑定；全体块体质继续按已有覆盖率计算。不同特性独立存在，例如鱼鳃可供水下呼吸，但不会取消末影人组织的遇水伤害。

## 四、分批施工与完成条件

1. **基础数据与存档链路**：在 `SurgicalSubject`、`SurgicalAssembly.Source` 及相关序列化/网络路径加入供体来源、原始角色全集、权重或模板引用；覆盖切割、提取、胶合、打包、拆箱、旧档读取。服务端建可信解剖注册表和逐项规则重载，缓存键包含类型、稳定变种、模板/规则版本；`/reload` 与重装配重新派生能力。完成条件：同一供体器官切成多份再组合仍只计算一次，旧档不凭未知完整度解锁新能力。
2. **头/鳃能力**：沿用 `BionicMind` 的头部路径，增加完整度和连通判定；实现水下呼吸、离水呼吸失败、屏息与可驯服。呼吸应在耗气/流体呼吸入口处理，不能全局取消 `drown` 伤害，否则会误消除烈焰人组织的水敏感。可驯服需要成品自己的主人数据、交互和跟随/坐下行为。完成条件：鱼鳃加末影人身体可水下呼吸且仍怕水；移除头后不能继续驯服；亡灵组织的无需呼吸保持独立。
3. **承重腿与地形**：用 `effectiveLimbs()`、落地腿数、体积负载实现灵巧落地、减轻摔落、细雪/熔岩表面行走和攀墙。完成条件：悬空猫腿不免摔、仅有蜘蛛躯干而没有腿角色不攀墙、炽足兽足能站熔岩但非抗火组织照常受伤。
4. **推进、交互与战斗器官**：实现成品飞行/游泳移动控制及导航切换，补充信任/合作模式与食物交互，再把毒性、凋零、饥饿和远程附效接到实际攻击器官与命中事件。现有攻击流程已记录左右手和臂槽，可在伤害成功时使用该快照；无远程攻击系统前不启用附效远程攻击。完成条件：普通臂攻击不继承另一只毒牙的效果；单翼或超载身体不飞行；无鳍的水下呼吸成品不自动快游；信任关系不被当成已驯服状态。
5. **姿态、感知与外部 AI**：实现壳防御状态、主动体表刺伤、感知、避水与威慑。威慑需要被威慑生物的回避判定也识别成品；必要的 mixin 只针对实际缺失的外部判定点，并按当前 NeoForge 映射规则编译及核查 refmap。完成条件：未缩壳时无闭壳护甲，猫头成品确实能让目标生物回避，而非只在面板显示词条。

每批都要同步手术台预览、纸箱属性文字和成品运行结果，明确区分“供体有此事实”“器官未识别”“器官不完整”“装配用途不符”与“能力已生效”。文档阶段不改动游戏逻辑；进入实现阶段仍遵守项目“不创建测试文件”的约束，按实际代码风险选择编译和手工场景核验。非 mixin 变更不启动客户端验证任务；涉及 mixin 时按仓库规则检查生成的 refmap，并在可行时运行 `quickPlaySmoke`。

## 五、当前实现与数据包格式

上述能力已拆为头部规则、器官规则和服务端解剖模板，并在成品中接入呼吸、驯服、食物、信任、移动、地形、近战附效、感知、威慑、体表刺和防御状态。新捕获、完整且从未切割的供体可按物种事实启用器官能力；切割后的供体必须匹配服务端模板，未知体块角色不会从客户端头部标记推导。连通体块按装配图筛选，同一供体 ID 的原始体块去重后计算完整度。旧存档没有可靠原始头部全集时，仍保留旧的性情与认知行为，但不因此开启新的特殊能力，除非其体块布局匹配服务端模板。

解剖模板放在 `data/<数据包命名空间>/bionic_anatomy/<生物命名空间>/<生物路径>.json`。同一种生物可有多个模板，例如在路径末尾增加 `/adult`、`/baby`，并用 `entity_type` 显式指定生物。字段包括：

| 字段 | 含义 |
| --- | --- |
| `entity_type` | 可选；明确指定生物 ID，适合一个生物的多个模型模板。 |
| `baby` | 可选；只匹配幼体或成体；省略时不限制。 |
| `cube_count` | 原始捕获体块总数，必须与供体匹配。 |
| `seams` | 原始接缝端点对数组，必须与供体原始拓扑严格匹配。 |
| `roles` | 解剖角色到原始体块 ID 数组的映射，可一块多角色；角色名见 `BionicAnatomyRole`。 |
| `weights` | 可选；每个原始体块的正数权重数组，缺省时等权。 |

每项特性的规则在 `data/<命名空间>/bionic_head_traits/` 或 `bionic_organ_traits/` 下。生物类型规则高于标签规则，`false` 可覆盖自动探测。器官规则还支持 `min_completeness`；`fall_reduction.json` 的 `parameters` 分别配置 `safe_fall_distance`、`damage_multiplier` 与 `flat_reduction`，近战效果、刺和缩壳也有持续时间等数值。承重腿规则可配置 `min_legs` 和 `max_body_volume_per_leg`，扑翼飞行使用模板权重累计升力。`long_breath.json` 的 `max_air_supply` 控制成品气量上限。

纸箱的原始供体页列出“供体特殊器官候选”；装配后纸箱与手术台预览只把通过完整度、连通和用途检查的能力列为已生效，并对未生效项区分“器官映射未识别”“不完整或未连通”“用途或负载不符”。附效远程攻击保留了规则 ID，但当前成品没有发射弹射物的攻击路径，因此解析时不启用，面板会注明缺少远程攻击路径。嗅探兽的植物搜寻尚未纳入“振动感知”；该项目前只对监守者供体启用。通用完整供体回退能让四批能力在未切割供体上工作；要使某一种生物的**部分**体块也可靠继承器官能力，需要为其具体捕获模型提供精确模板。
