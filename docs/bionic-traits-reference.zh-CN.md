# 仿生生物特性总表

本文按当前工作区代码与数据整理（Minecraft 1.21.1 / NeoForge），按生效规则分为三类；作用范围只分全身、躯干、头、臂、腿五种，后三种对应手术台实际提供的器官：

所有 42 项特性统一定义在 [BionicTrait](../src/main/java/com/nobodiiiii/createbiotech/entity/trait/BionicTrait.java)，统一由 [BionicTraitResolver](../src/main/java/com/nobodiiiii/createbiotech/entity/trait/BionicTraitResolver.java) 解析。原有三个 JSON 目录仅作为数据兼容入口，不再决定使用哪套解析器。

| 作用范围 | `BionicTraitScope` | 判定范围 | 本次归类 |
| --- | --- | --- | --- |
| 全身 | `WHOLE_BODY` | 全部保留体块，安装位置不限 | 原有全身体质、效果免疫、天然护甲、自然恢复、主动体表刺伤 |
| 躯干 | `TORSO` | 未归属头、臂、腿的保留体块 | 无翼飞行、身体弹跳、身体缓降、抗击退、缩壳防御 |
| 头 | `HEAD` | 通过颈关节安装的全部体块 | 水下呼吸、离水窒息、长时间屏息、可驯服、亲和合作、食物识别、振动感知、避水偏好、生物威慑 |
| 臂 | `ARM` | 肩关节及所属肘关节链的全部体块 | 扑翼飞行、毒性攻击、凋零近战、饥饿近战、附效远程攻击、游泳专长 |
| 腿 | `LEG` | 髋关节及所属膝关节链的全部体块 | 灵巧落地、减轻摔落、细雪行走、熔岩行走、攀墙、游泳专长 |

**游泳专长允许臂或腿**，分子、分母各取所有臂和腿体块的并集，只结算一次。其他特性各声明一个范围。鳃、足、左右翅、鳍、尾、触手、壳、刺、口器和攻击手只是供体模型的载体标签，不是额外可安装器官，也不能自动指定安装位置。

原有 `bionic_body_traits/`、`bionic_head_traits/`、`bionic_organ_traits/` 目录仅保留 JSON 路径兼容性，“呼吸”和“特殊器官”不再作为作用范围。

效果执行集中在 [SlimeBionicEntity.java](../src/main/java/com/nobodiiiii/createbiotech/entity/SlimeBionicEntity.java)，细雪行走另见 [PowderSnowBionicFootMixin.java](../src/main/java/com/nobodiiiii/createbiotech/mixin/PowderSnowBionicFootMixin.java)。

## 三类生效规则（代码中的明确分类）

类别定义在 `BionicTraitType`，统一判定在 `BionicTraitRule`。`BionicTrait` 的每个枚举项独立声明 `scopes()`（允许安装位置及占比范围）、`carrier()`（供体载体标签与回退规则）、`rule()`（三类生效规则）、`valueKind()`（能力、数值或效果集合）和 `condition()`（可选附加条件）；效果免疫和数值属性也属于同一目录。`BionicAnatomyRole` 只描述供体体块的标签；安装部位直接由 `BionicTraitScope` 描述，已删除会按解剖标签推断安装位置的 `BionicTraitSlot`。

| 类别 | 代码 | 获取与效果 | 当前归类 |
| --- | --- | --- | --- |
| 1. 存在型 | `PRESENCE` / `presence()` | 对应部位只要保留了载体就获得完整特性；不设占比下限，不随占比衰减，也不要求记录了体积 | 可驯服、亲和合作、食物识别、振动感知、避水偏好、生物威慑、毒性攻击、凋零近战、饥饿近战、主动体表刺伤 |
| 2. 门槛型 | `COVERAGE_THRESHOLD` / `threshold(...)` | 占比达到门槛，并满足可选附加条件后，获得固定效果；未达标时不获得部分效果 | 治疗反转、摔落免疫、无视蛛网、无需呼吸、无翼飞行、弹射物偏转；水下呼吸、离水窒息、长时间屏息；灵巧落地、减轻摔落、细雪行走、熔岩行走、攀墙、扑翼飞行、游泳专长、附效远程攻击、缩壳防御；效果免疫 |
| 3. 比例型 | `COVERAGE_SCALED` / `scaled()` | 正占比即贡献效果，强度、概率或数值随占比变化 | 火焰免疫、遇水受伤、冻结抗性、冻结易伤、阳光灼伤、保湿依赖、高温灼伤、身体弹跳、身体缓降、接触反伤；天然护甲、抗击退、自然恢复 |

- “存在”指**匹配供体、仍然保留、属于特性有效范围**的载体。安装位置只按每项特性的 `scopes()` 检查。全身范围不限制安装位置；需要特定载体的特性仍检查 `carrier()`，例如体表刺伤需要刺体块。切掉载体就不再贡献。存在型不会被其他供体的同部位组织稀释。
- 存在型的获取条件与使用时机不同。例如毒性攻击仍需由带毒器官所在的攻击臂命中；饥饿近战仍需空手；振动感知仍在敌对且无目标时找目标。
- 门槛型默认 50%；各目录 JSON 的 `min_coverage` 只作用于门槛型，存在型不读取它。效果免疫默认为 100% 门槛，取全身所有有体积贡献的供体免疫集合的交集。
- 附加获取条件由解析器统一检查，预览和实体共用：腿类检查落地腿数与承重；扑翼飞行检查手臂范围占比、双翼载体是否都在场和翅膀承重；离水窒息受“无需呼吸”抑制；附效远程攻击尚无发射路径，因此不生效。
- `BionicTraitSet.coverage()` 只表示原始占比，`has()` 表示是否获取特性，`strength()` 返回实际系数（门槛型为 0/1，比例型为占比）。实体效果不再自行硬编码 50% 判定。
- 特性提示只使用“全身、躯干、头部、手臂、腿部”五组，跨部位的游泳专长只展示一次并标注“手臂、腿部”，只对比例型显示部分占比；门槛型未达标时显示“所在部位占比不足”。
- 当前版本已通过 `BionicTraits.ENABLED = true` 启用特性功能；这是代码中的发布开关，不是存档配置项。

## 代码职责与扩展入口

| 层 | 入口 | 职责 |
| --- | --- | --- |
| 特性定义 | `BionicTrait` / `BionicTraitScope` / `BionicTraitRule` | 定义特性、贡献组织和获取规则 |
| 数据加载 | `BionicTraitDataLoader` | 统一校验 JSON、合并供体覆盖、读取载体和参数；一个文件只解析一次 |
| 数据版本 | `BionicTraitRegistry` | 保存不可变数据快照；数据或实体标签更新时提升版本 |
| 供体事实 | `BionicTraitDonors` | 对同一生物档案只重建一次供体，检测所有特性；缓存按世界和数据版本隔离 |
| 组织测量 | `BionicTissue` / `BionicTraitCarriers` / `BionicAnatomyRegistry` | 按安装范围选择分母，再按供体标签筛选分子；角色不参与分母筛选 |
| 装配解析 | `BionicTraitResolver` / `BionicTraitConditions` | 先统一计算覆盖率，再检查承重和特性依赖 |
| 解析结果 | `BionicTraitSet` / `BionicTraitResult` | 同时保存占比、实际强度、数值、免疫集合、载体和未生效原因 |
| 消费结果 | `SlimeBionicEntity.getBionicTraits()` / 手术台及纸箱 Tooltip | 实体执行效果，提示展示同一判定；不再为了原因额外解析 |

新增同类特性时，在统一目录独立声明安装范围、载体、规则和返回值类型，并在对应兼容目录补 JSON。只有新的自动探测方法、附加条件或游戏效果才需要扩展相应层。三个旧的身体/头部/器官特性枚举、独立解析器、结果类型及重复载体加载器已经移除。

## 一、通用规则

### 1. 供体判定优先级

每项特性对供体物种的判定顺序为 **自动探测 < 实体标签（`#tag`）< 单个实体 ID**，`false` 可撤销低优先级结果。JSON 中 `automatic_detection: false` 时只看 `values`。

所有目录现在采用同一覆盖顺序：先读 `create_biotech` 的规范文件，再按资源 ID 排序合并其他命名空间的同名文件；匹配标签按资源 ID 排序应用，最后应用精确实体 ID。规范文件控制规则、参数和载体，其他命名空间的 `values` 扩充供体。旧头部/器官加载器曾把规范文件混在命名空间排序中，本次统一为扩展文件可以覆盖默认值。

非法布尔值、负数、非有限数值和越界门槛被忽略并记录警告，保留默认值；存在型和比例型不读取 `min_coverage`。

### 2. 体块体积

- 所有覆盖率都按体块**体积**加权。体积取捕获时每个模型体块的实际尺寸（方块³）；不足 1 像素的边按 1 像素计，因此平面的翅、鳍也有体积。
- 旧存档中未记录体积的来源计为 0 体积，不回退到按体块数加权。存在型仍能按保留载体判断；门槛型和比例型依赖有效体积。

### 3. 躯干与全身覆盖率

```
躯干覆盖率(特性) = Σ(具备该特性的供体安装在躯干的保留载体体块体积) / Σ(安装在躯干的全部保留体块体积)
全身覆盖率(特性) = Σ(具备该特性的供体在全身任何部位的保留载体体块体积) / Σ(全身全部保留体块体积)
```

- **躯干范围**：无翼飞行、身体弹跳、身体缓降、抗击退、缩壳防御。其中缩壳防御只由壳标签载体贡献分子。头、手臂、腿等部位不参与这些特性的分子或分母。
- **全身范围**：其余体质特性，以及效果免疫、天然护甲、自然恢复、主动体表刺伤。头、臂、腿以及躯干上的任意载体均可贡献，不要求保留躯干，也不要求原始器官角色与安装部位匹配；主动体表刺伤另外筛选刺标签载体。
- 两种范围分别累计总体积。没有该特性的组织仍计入对应分母；已切除的体块不计入任何范围；同一保留体块在一个范围中只计算一次。
- 例如：普通躯干体积 6、烈焰人手臂体积 2、普通头部体积 2，全身火焰抗性覆盖率为 `2 / (6 + 2 + 2) = 20%`；烈焰人手臂不会提供躯干范围的身体缓降。
- 数值项在各自范围内按体积加权平均：天然护甲和自然恢复按全身，抗击退按躯干。没有躯干体积时，躯干数值为 0，全身数值仍正常计算。
- 效果免疫是全身范围的 100% 门槛：取**全身所有有体积贡献**的供体免疫集合的**交集**；任意器官混入不免疫的组织，便失去该项完整免疫。
- 原有 JSON 路径和特性 ID 保持兼容；每项特性的范围由枚举中的 `scopes()` 明确声明。

### 4. 按装配范围计算覆盖率

所有特性使用同一条计算路径：

```
覆盖率 = Σ(供体有该特性、载体匹配、装在允许范围内的保留体块体积)
       / Σ(允许范围内全部保留体块体积)
```

- **分母只看装配位置**：头部特性取全部装成头的体块，扑翼/攻击特性取全部装成臂的体块，腿类特性取全部装成腿的体块，缩壳取全部躯干体块。没有角色标签或不具备该特性的普通组织也计入分母。
- **分子再看载体**：供体物种具备该特性，且体块符合该特性 JSON 的 `carriers`（模型部件名或 `#体块ID`）；缺少可用声明时可使用捕获头部、解剖快照、已知模型部件名或 `bionic_anatomy/` 模板。全组织体质不筛选载体标签。
- 呼吸特性只允许装在头部。供体原本能识别到鳃时使用鳃；原本没有鳃映射时回退到头部。切掉已知鳃不会重新回退到普通头部。
- 翅膀装成臂即可提供扑翼飞行；装在躯干或腿不计入。左、右翼载体合并计算臂范围占比，达到门槛后还须两种载体均在场且升力足够。
- 鳍、尾、触手或腿体块装成臂或腿均可提供游泳专长。覆盖率以全部臂、腿体块为分母，两个范围合并去重，不把躯干体积算进来。
- 口器或毒刺装成臂可提供毒性攻击；装在头部或躯干不会提供近战附毒。体表刺伤则允许刺体块位于全身任意器官。
- 同一标签不意味着同一种安装限制：毒刺的近战附毒需要装成臂，体表刺伤没有安装位置限制。
- 不额外要求几何相连；切除的体块既不进分子也不进分母。存在型只要求允许范围内有匹配载体；门槛型和比例型按上述体积占比判断。
- 解析结果记录有效载体 `members`；攻击类效果只由包含相应载体的攻击臂命中时触发。

### 5. 需要腿的器官特性

灵巧落地、减轻摔落、细雪行走、熔岩行走、攀墙额外要求：

- `成品落地腿数 ≥ min_legs`（灵巧落地、攀墙默认 2，其余默认 1）。
- 载体腿体积必须大于 0；已有身体体积时，要求 `身体体积 ≤ 载体腿体积 × max_body_volume_per_leg_volume`（默认 32）。

### 6. 未生效原因（Tooltip）

| 原因键 | 显示文本 | 触发情形 |
| --- | --- | --- |
| `insufficient_coverage` | 所在部位占比不足 | 载体体块在场，但局部覆盖率低于门槛 |
| `missing_paired_wings` | 缺少成对的翅膀 | 臂范围占比已达标，但缺少左翼或右翼载体 |
| `body_measurement_unavailable` | 身体测量结果暂不可用 | 腿类特性缺少身体尺寸数据，或扑翼飞行缺少身体体积数据 |
| `purpose_mismatch` | 装配用途或负载不符 | 覆盖率足够，但落地腿数或负载不满足 |
| `wrong_slot` | 未装在对应部位 | 载体仍在，但没有装在该器官对应部位 |
| `breathing_not_required` | 无需呼吸，离水窒息不生效 | 已获取“无需呼吸”，抑制离水窒息 |
| `no_ranged_attack` | 成品没有远程攻击路径 | 附效远程攻击（目前恒不生效） |

载体体块已全部切除，或该物种的载体无法识别时，不显示原因。
